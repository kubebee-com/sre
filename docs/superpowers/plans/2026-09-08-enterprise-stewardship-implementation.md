# Stewardship and scoped reviewed knowledge

Implement the reviewed-learning portion of the enterprise program after immutable feedback, evidence lineage, and independent recovery exist.

1. Adjudication: append immutable events against exact item reference/hash and visible feedback IDs. Reasons CONFIRMED, FACTUAL_ERROR, NOT_APPLICABLE, STALE, UNRESOLVED; authorized Steward only. FALSE/FACTUAL_ERROR keeps quarantine. Do not silently lift quarantine or mutate historical body. Conflicting prior feedback remains visible. Stable hashed idempotency keys; correction refers to exact fresh replacement evidence references and a reason code, never raw customer prose.
2. Corroboration: Steward submits exact current CLAIM hash and independent causal rubric attestation (upstream checked, temporal order checked, material alternatives tested) with current scoped evidence. Re-evaluate deterministic AssessCandidate and independently detect healthy contradictions; require a causal code (NETWORK_BLOCKED, CONFIGURATION_DRIFT, RESOURCE_PRESSURE), not a symptom code. Require at least two distinct direct/discriminating evidence refs. The model cannot invoke this authority. Publish a new immutable CORROBORATED CLAIM with evidence and original claim parents, short evidence-bounded validity, actor/rubric metadata, never edit original claim.
3. Golden candidate: explicit Steward creates scoped candidate from a corroborated claim and a persisted RECOVERED assessment for the same incident. Check all historic claim/recovery lineage Uncontested, source authority epoch/current revocation, and an independently recorded recovery window. Recovery is not causal proof; corroboration supplies that separately. Store source reference/hash and recovery ID, immutable versioned strict content derived from codes/opaque references only. No direct raw generic item body copied into knowledge.
4. Publication: a separate explicit Steward review action publishes candidate only after passing frozen baseline evaluation; record evaluator identity/version, positive and negative fixture counts, score, and no-regression result. Evaluate using deterministic scenario rubric in code, not caller-provided pass booleans. Candidate author cannot review own publication. Frozen/held-out sets distinct, new release requires both. Immutable releases with current ACTIVE/RETIRED status separate. Retire route requires Steward.
5. Retrieval: same-scope only, published active release only, synchronous source/recovery lineage dispute and revocation checks. Historical freshness does not itself erase golden cases, but new diagnoses may only use them as guidance, requiring independently collected current evidence. Knowledge can never authorize cluster actions or change permissions, providers, prompts or tools. No auto promotion from True feedback.
6. Metrics: all CLAIM RunResults count as diagnostic attempts, including provider failures and abstentions. Reviewed correctness denominator comes from latest relevant adjudication per exact item, FACTUAL_ERROR versus CONFIRMED only; NOT_APPLICABLE/STALE/UNRESOLVED remain separate. Return sample counts, reviewed coverage, abstention/provider failure fractions, factual success interval (Wilson), and daily/profile/version cohorts. Unknown correctness is null. Include sustained recovery totals separately; never equate APPLIED with success. Add frozen metrics tests with small cohorts and conflicting/contextual adjudications.

Use migrations 007 onward; root owns schema 006 environment. Shared transaction APIs and domain types live in pkg/incident, postgres; services in pkg/stewardship and pkg/knowledge. Do not create HTTP/UI yet; root integrates shared services. Tests must exercise real PostgreSQL when SRE_ENTERPRISE_TEST_DATABASE_URL exists and fail safely without authority; pure rubric/metric fixtures always run.

Implementation note: historical source revocation must be checked against the stored agent's explicit revoked flag and authority epoch; routine credential expiry/renewal alone should not rewrite historical truth. A current diagnosis still requires fresh Eligible observations. Keep this distinction visible in APIs and tests.
