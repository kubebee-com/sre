# Customer-hosted enterprise SRE

The enterprise entry point is `sre-control-plane`. It serves the scoped HTTPS-facing UI/API using PostgreSQL and OIDC. Each application/cluster has its own read-only collector and optional executor. The control plane has no Kubernetes client credentials. The legacy `sre-agent` HTTP/gRPC/MCP/chat/harness surfaces are not an enterprise authentication gateway and must not be exposed alongside it as an alternative access path.

The first executable action is replacement of one unhealthy, controller-managed Pod. Unknown actions, shell commands, generic apply/patch, exec, port-forward, Secret reads, privilege changes, bulk deletion, arbitrary CRDs, cloud writes and GitOps writes are denied/unsupported. An applied Pod deletion is a mitigation attempt, not proof of a root cause or application recovery. Other repairs remain human operations and cannot be activated through AI prompts.

## Build and deploy

`make enterprise-build` builds the control plane, collector, executor, secret initializer and engineer CLI and offline evaluator under `bin/enterprise`. Build separate images with `deploy/Dockerfile.enterprise` targets `control-plane`, `collector`, `executor`, `agent-init`. Set chart image repositories/tags to your reviewed images; the example repository names do not assert that images have been published. Publish/sign/scan through your release process before production use.

Use `deploy/helm/sre-enterprise`; it installs one control-plane replica with Recreate rollouts, token automount disabled and no workload RBAC. Collectors/executors have separate Pods, ServiceAccounts and private credential PVCs. Only their encrypted identity mapping PVC is shared; the executor mounts it read-only. `OnRootMismatch` prevents ordinary volume remounts widening private registry/credential permissions. Use a CSI driver that honors these permissions. The two agents are colocated for the default ReadWriteOnce volume. Multiple control-plane replicas are not supported.

Create a ConfigMap with key `config.json` from `deploy/examples/enterprise/config.json`. Scopes are immutable organization/cluster/application IDs. Owner groups and delegated approver groups come from trusted deployment configuration, not labels or model output. Additional bindings grant explicit Viewer, Investigator, Steward, Administrator or Security Administrator roles; administrator setup authority does not imply access to incident evidence. Every application should have an authorized setup administrator. Namespace allowlists are explicit per collector; shared infrastructure should have its own platform-owned application scope. Avoid overlapping application namespace assignments unless deliberately reviewed. Environment setup records topology, platform, criticality, dependencies and integration availability as typed administrator context. It grants no cross-application data access.

The control-plane Secret must provide:

| Variable | Value |
|---|---|
| `SRE_ENTERPRISE_DATABASE_URL` | PostgreSQL DSN using verified TLS, normally `sslmode=verify-full`; unverified/fallback plaintext is rejected. |
| `SRE_ENTERPRISE_PUBLIC_URL` | Exact external HTTPS origin. |
| `SRE_OIDC_ISSUER` | HTTPS issuer with discoverable signing keys. |
| `SRE_OIDC_CLIENT_ID` | Registered application audience/client ID. |
| `SRE_OIDC_CLIENT_SECRET` | OAuth client secret for browser login. |
| `SRE_AUTHORITY_GENERATION` | Operator-managed authority generation; change after restore/security reset. |

Register redirect URI `<public-url>/auth/callback`. Browser sessions use OIDC authorization code + PKCE, short-lived identity, secure cookies and CSRF checks. API/CLI accepts verified bearer identity with the same scope policy. Group changes take effect on the next validated identity; maximum identity lifetime is 15 minutes. No caller identity headers substitute for OIDC. Configure your IdP accordingly.

Terminate TLS at a trusted ingress. Restrict direct access to the internal HTTP service. Enable the chart TLS ingress and configure database CIDRs; the default NetworkPolicy does not permit database egress until CIDRs are supplied. Configure your Kubernetes API port explicitly when it differs from 443. DNS and HTTPS egress are allowed; restrict approved provider/IdP destinations further with the customer's egress gateway. `tlsCASecret` optionally mounts a Secret with `ca.crt` as the Go trust bundle for private PKI. A PostgreSQL private CA can also be referenced with `sslrootcert=/etc/sre-trust/ca.crt` in its DSN. Never disable TLS verification to onboard a private cluster.

## Enroll each application and cluster

Verify the intended cluster with an administrator kubeconfig and obtain the UID of the `kube-system` Namespace. Enter that UID, the scope and explicit namespace allowlist into the per-cluster values. `collector-a.yaml` shows an agent-only remote installation; create a second values file with cluster B's distinct ID and verified UID. An agent verifies the live UID before enrollment or collection; the default kubeconfig/current context is never inferred.

An administrator uses Application and cluster setup to issue a role-specific bootstrap for `COLLECTOR` or `EXECUTOR`. Bootstrap tokens expire after ten minutes and are consumed once. Store the token in the role's Secret key `token`. Generate 32 random bytes for the local identity Secret key `key`; keep it within that cluster's administrative boundary. Do not copy agent bearer credentials into the shared identities volume. The initializer writes private 0600 files under 0700 directories. Collectors send only allowlisted observations, numeric metrics and opaque identities. Raw names, logs, events, specs, annotation values and customer data do not leave the local projection boundary.

Enable the collector first. The UI lists its role, credential generation, expiry and revocation. Register a versioned application-health profile selecting the required Deployment handles, minimum ready replicas, minimum samples, maximum gap and sustained window. Unknown/partial coverage, stale data, disputed health evidence and source changes cannot establish recovery. The deployment must have observed its current generation and have the desired updated/available/ready replicas.

Execution requires both `controlPlane.executionEnabled: true` and the separate per-cluster `executor.enabled: true`. The executor receives only Pod get/delete and controller get RBAC in the explicit application namespaces. System/agent namespaces and protected resources are denied. Owners approve an exact hash, evidence version, opaque target commitment, UID/resourceVersion and expiry; no conversational acknowledgement grants permission. Live preconditions and independent journal state are checked around one dry-run and one non-retried mutation. A stale plan requires fresh evidence and a new owner approval. Missing receipts stay unresolved; after 120 seconds an owner may explicitly record AMBIGUOUS. This never retries an operation. A later authenticated executor receipt acknowledges that terminal reconciliation without overwriting AMBIGUOUS; the local journal retains its original outcome and can proceed to newly authorized work. Any rollback or further repair needs its own new plan/approval.

## Providers and privacy

Add governed provider entries to `providers` with an ID, provider/model, optional HTTPS endpoint, permitted scopes and an API-key environment reference plus `credential_version`. Existing adapters support OpenAI, Claude, Gemini, Azure OpenAI, Bedrock and configured compatible/self-hosted endpoints. Each profile is versioned from its trusted configuration. Engineers select only profiles permitted for their application. The `rule` profile performs no inference and returns a need for evidence; it does not simulate AI diagnosis. Provider calls have 20-second deadlines, 2048 output-token caps, bounded request/response sizes and at most three diagnostic rounds. Availability and actual account/model support require customer provider contract tests.

The enterprise privacy floor is strict projection, outside the model. There is no prompt, operator setting or feedback text field that enables raw customer disclosure. Corrections use enumerated reasons and visible immutable evidence references. Typed fresh-collection requests can only cause another scoped read-only scan. Operators govern provider region, retention/training terms and private endpoint trust outside AI. General service logs/errors and notification bodies exclude customer content. Backups still contain sensitive organizational metadata and must be protected.

## Engineer review and learning

Every observation and conclusion has True, False and Cannot verify choices, optional reasons, exact version/hash binding and attributed immutable history. False immediately quarantines the item and its descendants; True does not undo quarantine. A fresh investigation uses remaining current observations, not previous guesses. Stewards adjudicate factual errors separately from stale/non-applicable context and can corroborate only an explicitly tested causal hypothesis with independent evidence and reviewed alternatives.

After sustained recovery, a steward can nominate a golden case; a different steward must evaluate and publish it. The initial eight fixed positive/negative/held-out checks evaluate safe guidance selection, not real-world provider accuracy. Production uses that same applicability predicate. Historical guidance is never current evidence. Its source and recovery lineage remain attached to derived diagnoses, so later disputes or revocation propagate synchronously. Retired/disputed releases cannot guide new investigations. Nothing in learning can change permissions, tools, privacy or approval policy.

The dashboard reports attempts, unique eligible/reviewed/corroborated incidents, diagnostic coverage, verified diagnostic yield, abstentions, provider failures, invalidated results and factual correctness with 95% Wilson intervals by day/profile/version. Retrying one incident cannot create multiple successful incidents. Revoked or quarantined source lineage removes the result from current valid success counts; normal historical expiry alone does not. Unreviewed results are unknown, not successes. Recovery counts are independent observations, not attribution to a repair. Provider round latency and available token accounting are retained in conclusion details; missing usage remains unknown and monetary cost is not fabricated. Changing case mix and small sample sizes do not prove improvement. `make enterprise-evaluate` runs the [frozen paired comparison](evaluation-rubric.md); `sre-evaluate` also compares hash-bound recorded provider outputs without making live calls or changing production knowledge.

## Notifications and operations

Trusted notification routes bind an ID, exact scope, recipient group and HTTPS endpoint environment reference. Set optional escalation route/delay for an authorized group in the same scope. The destination must accept a small JSON payload (`id`, `scope`, `kind`, `incident_id`) and honor `Idempotency-Key`; delivery retries can duplicate external receipts. This is a generic webhook contract, not native email/Slack formatting. Public HTTPS endpoints on port 443 are supported; private/link-local destinations and redirects are rejected. Customer-owned relays can adapt delivery to their messaging system.

Routes register at startup; a newly registered route starts with new events, while an existing route preserves its backlog. Each send rechecks group access. Eight bounded attempts, leases, acknowledgements and escalation survive process restarts. Only owners/designated approvers can acknowledge deliveries; acknowledgement is not mutation approval. Scope-specific operations show agent state, jobs, actions, quarantine counts and notification backlog; unavailable reads are displayed as unknown. Health/readiness probes reveal no incident data.

`retention_days` is trusted configuration (default 90; 7–3650). Hourly bounded maintenance deletes old report-dedup receipts/expired bootstrap material and clears expired encrypted terminal-job authority. It intentionally preserves immutable evidence, reviews, action audit, revocations, recovery and golden lineage. Plan storage capacity for these retained records. Full historical erasure requires retiring the affected knowledge and deleting the customer-owned database/backups under the customer's retention process; this release does not claim automatic safe pruning of arbitrary historical lineage. No raw customer content is stored for a raw-log retention job to erase.

## Backup, restore, upgrades and rotation

Back up the PostgreSQL database and encrypted local identity volumes with tested customer-owned tooling; store encryption keys and provider/OIDC secrets separately. Verify checksummed migrations on a restored isolated database before upgrading. Never restore directly into an active executor fleet. A restore/startup creates a new random authority epoch in addition to the configured generation. This invalidates old agent tokens, pending approvals and queued engineer authority even when restored rows say they are valid. Old learning provenance is ineligible until rebuilt from freshly reviewed evidence. This conservative first-release choice also means every ordinary control-plane restart requires agent re-enrollment and new approvals; schedule maintenance accordingly.

To re-enroll, revoke the old registration, issue a new one-use bootstrap, stop the affected agent, replace its private credential file through the authorized local administration process, update its bootstrap Secret and restart it. Do not auto-delete a rejected credential or silently bootstrap from an old Secret. Collector renewal rotates generation; approvals tied to older evidence become unusable. Identity-key rotation requires a new registry and re-enrollment; old exact commitments cannot be executed. Preserve unresolved executor journal records during recovery. Never copy a previous journal or approval to authorize a new operation.

Run `make enterprise-test`, `scripts/ci/enterprise-chart.sh`, and `scripts/ci/enterprise-kind.sh` in disposable environments. The Kind script creates/removes only uniquely named test resources and uses explicit kubeconfigs. Browser testing is enabled with a pinned Playwright module and Chromium executable. It does not contact real notification destinations or paid AI providers. These are acceptance checks, not a production certification or an HA/scale guarantee.

## Reproducible limits and security evidence

The [capacity measurement](enterprise-capacity.md) covers 1,001 synthetic incidents across two cluster scopes. Quality lineage queries are substantially more expensive than simple operational reads; avoid aggressive dashboard polling. One investigation accepts at most 64 eligible observations and fails visibly above its supported snapshot bound. Per-scope queues hold at most eight active jobs; the control plane runs two investigations concurrently, each with three provider calls and a 90-second budget. Local identity registries hold at most 10,000 resources. These bounds are safeguards, not a production throughput guarantee.

CI builds all four enterprise images, blocks high/critical image findings and retains full Trivy reports and CycloneDX SBOMs. The local 2026-09-08 scan used Trivy 0.74.0 and Go 1.26.6: no reachable Go vulnerabilities or high/critical image findings; one control-plane module advisory concerns the unused `golang.org/x/crypto/openpgp` package. Full reports retain this finding. Release image signing/publication remains part of the customer's trusted registry process. No production credentials, real notifications or paid model calls are needed for the repository acceptance tests.
