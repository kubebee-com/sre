# Messaging channels

The orchestrator owns messaging; agents need no IM credentials. Multiple channels can run together. Every outgoing route retains the existing PostgreSQL delivery queue, recipient authorization, retries and escalation. Notification acknowledgement is separate from action approval.

| Provider name | Outbound transport | Direct commands |
| --- | --- | --- |
| `slack` | Incoming webhook, Block Kit and UI link | Signed `/sre` slash command |
| `teams` | Workflow webhook, Adaptive Card and UI link | Use authenticated UI |
| `discord` | Incoming webhook, message and UI link | Signed `/sre` application command |
| `telegram` | Bot API `sendMessage` | Secret-authenticated webhook `/sre` command |
| `google_chat` | Space webhook, message and UI link | Use authenticated UI |
| `whatsapp` | Cloud API approved template | Use authenticated UI |
| `matrix` | Client API room message with transaction ID | Use authenticated UI |

This adopts the shared gateway/channel-adapter pattern described by [OpenClaw](https://docs.openclaw.ai/channels). It does not provide its general chat assistant, media, voice, dynamic plugins, or WhatsApp QR pairing.

## Outgoing routes

Add entries to `notifications` in the orchestrator JSON configuration. Each entry uses either a typed `channel` or the existing generic `endpoint_env`, never both. Secrets are environment variable references, not literal values in JSON.

```json
{
  "id": "payments-slack",
  "scope": {"organization_id": "acme", "cluster_id": "prod", "application_id": "payments"},
  "recipient_group": "payments-owners",
  "channel": {"provider": "slack", "endpoint_env": "SRE_SLACK_WEBHOOK"},
  "escalation_route_id": "payments-oncall",
  "escalate_after_seconds": 300
}
```

`payments-oncall` must be another configured route in the same scope; omit both escalation fields when escalation is unnecessary. The recipient group must have scoped read permission. An escalation route can use a different platform.

Use these channel objects inside a route:

```json
{"provider":"teams","endpoint_env":"SRE_TEAMS_WEBHOOK"}
{"provider":"discord","endpoint_env":"SRE_DISCORD_WEBHOOK"}
{"provider":"telegram","token_env":"SRE_TELEGRAM_BOT_TOKEN","destination":"-1001234567890"}
{"provider":"google_chat","endpoint_env":"SRE_GOOGLE_CHAT_WEBHOOK"}
{"provider":"whatsapp","endpoint_env":"SRE_WHATSAPP_MESSAGES_ENDPOINT","token_env":"SRE_WHATSAPP_TOKEN","destination":"15551234567","template":"sre_notification","language":"en_US"}
{"provider":"matrix","endpoint_env":"SRE_MATRIX_HOMESERVER","token_env":"SRE_MATRIX_TOKEN","destination":"!room:matrix.example.com"}
```

Configure the endpoint variables as follows:

- Slack: an incoming webhook URL under `https://hooks.slack.com/services/`.
- Teams: a Teams Workflow webhook accepting an Adaptive Card message. Use the webhook URL generated by the workflow. Configure workflow ownership and availability for your organization. See [Microsoft's webhook setup](https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook).
- Discord: a Discord webhook URL under `https://discord.com/api/webhooks/`.
- Google Chat: the space's `https://chat.googleapis.com/v1/spaces/.../messages?key=...&token=...` webhook. See [Google Chat webhook setup](https://developers.google.com/workspace/chat/quickstart/webhooks).
- WhatsApp: `https://graph.facebook.com/vXX.X/PHONE_NUMBER_ID/messages`, using a supported Graph API version. Create and approve a template with four body text parameters in this order: notification kind, incident ID, notification ID, authenticated SRE URL. This supports proactive notifications outside the conversation window through approved templates; it does not use an ordinary text message or personal WhatsApp account.
- Matrix: the HTTPS homeserver origin, for example `https://matrix.example.com`, and a token for an account already joined to the destination room. The adapter sends plain `m.room.message`; encrypted rooms are unsupported.

All routes require public HTTPS endpoints. The HTTP transport rejects private-address destinations and redirects. Messages contain fixed identifiers and a scoped link to `SRE_PUBLIC_URL`, rather than raw logs or diagnostic prose. Configure a public HTTPS SRE origin before enabling typed notifications.

Delivery is at least once: a provider may accept a message immediately before a connection fails, resulting in another attempt. Matrix uses the notification ID as its native transaction ID. Do not assume the generic HTTP idempotency header deduplicates other providers. Rate-limit and provider failures enter the existing retry lifecycle. Teams URLs must use a `*.logic.azure.com` or `*.environment.api.powerplatform.com` host, an `/invoke` path and a `sig` query parameter; legacy Office 365 Connector URLs are unsupported.

## Incoming human commands

Add a separate `messaging` array to the same configuration. It binds a provider account, conversation and exact external user IDs to local principals/groups. Outgoing webhook credentials do not grant command authority.

```json
{
  "id": "payments-slack",
  "provider": "slack",
  "secret_env": "SRE_SLACK_SIGNING_SECRET",
  "account_id": "T0123456789",
  "conversation_id": "C0123456789",
  "scope": {"organization_id": "acme", "cluster_id": "prod", "application_id": "payments"},
  "users": [{"external_id":"U0123456789","principal_id":"alice","groups":["payments-owners"]}]
}
```

The callback URL is `https://sre.example.com/channels/payments-slack/events`. Expose it through the orchestrator ingress. It authenticates platform requests directly, while the UI/API retain OIDC authentication. Apply changes by restarting all orchestrator replicas with the same configuration and secret values.

- **Slack:** create a `/sre` slash command whose Request URL is the callback above. Set `account_id` to the workspace/team ID and configure the app signing secret. Verification covers the raw request body and timestamp. Display names and email addresses are not identity bindings.
- **Discord:** register `/sre` with one required string option named `command`. Set the app's interactions endpoint to the callback, `account_id` to the guild ID, `conversation_id` to the channel ID, and `public_key` to the application's hexadecimal Ed25519 public key. Omit `secret_env`. Use numeric Discord user IDs in `users`.
- **Telegram:** use `provider: telegram`, the bot username without `@` as `account_id`, numeric chat ID as `conversation_id`, and a separate strong webhook `secret_env`. Configure `setWebhook` with the callback URL and that secret as `secret_token`; do not use the bot token as the webhook secret. Use numeric Telegram user IDs. Each Telegram configuration needs its own unique webhook secret. Configure webhook updates for ordinary messages; edited messages and bot messages do not execute commands.

Available command text after `/sre`:

```text
approve ACTION_ID EXACT_64_CHARACTER_LOWERCASE_SHA256_HASH
reject ACTION_ID
answer REQUEST_ID VERSION ANSWER_CODE
ack NOTIFICATION_ID
```

Discord takes that text as the `command` option. Obtain current IDs, action hashes, versions and allowed answer codes from the authenticated UI/API. The bot does not infer consent from ordinary chat or natural-language replies.

Users need scoped `Approve` permission for approve/reject/ack and `Investigate` for answers. User mappings are trusted deployment configuration and must match your authorization bindings. Unknown users, other rooms/accounts, invalid signatures, stale requests and unsupported commands are rejected. No IM command creates a new investigation or directly executes a cluster operation. The executor still claims an approved, current action through its existing authenticated protocol.

The existing database transitions fence duplicate approvals and clarification answers; repeated notification acknowledgements are idempotent. There is no process-local replay cache required for correctness across HA replicas. The original actor is recorded by the same audit services used by the UI. Slack/Discord receive a command acknowledgement; Telegram's successful webhook acknowledgement is HTTP-only, so inspect the UI for operation status. Temporary storage failures return HTTP 503 to permit provider retries; permanent policy or state rejections receive a final acknowledgement. Command execution has a two-second context deadline to leave time for the platform response.

## Helm

Put configuration in the ConfigMap named by `orchestrator.existingConfigMap`. Put webhook URLs, tokens and signing secrets in the Secret named by `orchestrator.existingSecret`; the chart imports its keys as environment variables. Never place these secrets in agent values or agent provider credentials. The existing ingress forwards callback paths, and the chart permits HTTPS egress. No additional agent RBAC is required.

## Verification

Run `go test -p 1 ./pkg/messaging ./pkg/delivery ./pkg/orchestrator` for unit tests. Set `SRE_ENTERPRISE_TEST_DATABASE_URL` to an isolated migrated test PostgreSQL database to include durable delivery and policy integration tests. Tests use signed synthetic callbacks and mocked HTTP transports; they do not post to real IM services.

CI enforces at least 90% statement coverage separately for the incoming messaging package and the new outbound adapter file. Run `./scripts/ci/messaging-coverage.sh` to check locally.

### End-to-end regression suite

With an isolated PostgreSQL database, run:

```sh
SRE_ENTERPRISE_TEST_DATABASE_URL='postgres://…' ./scripts/ci/messaging-e2e.sh
```

The runner refuses to run without a database URL, and CI supplies its disposable PostgreSQL service. It enables the race detector and forces uncached execution.

- `pkg/orchestrator/messaging_approval_e2e_test.go`: HTTP proposal → notification → acknowledgement (still unapproved) → signed Slack/Discord/Telegram approval → executor claim → receipt → persisted outcome, audit and notifications. Includes rejection, forged requests, unauthorized users, wrong hashes, and concurrent duplicate approvals across replicas.
- `pkg/orchestrator/clarification_e2e_test.go`: HTTP clarification creation → durable notification → signed acknowledgement and answer → state read from another replica. Verifies acknowledgement does not answer the question, stale/invalid answers fail, and replay produces no duplicate audit events.
- `pkg/delivery/notification_e2e_test.go`: PostgreSQL outbox → delivery worker → native HTTPS requests for all seven providers → persisted delivery status. Covers HTTP 500/429 backoff, retry exhaustion, concurrent replicas, escalation, acknowledgement suppression, and revoked recipient access.

These tests use actual HTTP servers, PostgreSQL transactions and application services. The identity provider and external IM endpoints are local test substitutes, and the executor receipt is simulated; they do not send live messages or mutate a Kubernetes cluster. Notification timing tests advance only their own scoped test rows instead of waiting for retry/escalation timers.
